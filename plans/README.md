## Chosen architecture

- **Repository:** npm workspaces orchestrated by Turborepo.
- **Website:** Vite-powered React Router Framework Mode, React, TypeScript,
  Tailwind CSS, and shadcn/ui. The client-rendered catalog and detail routes load
  runtime data from the read-only API; they do not prerender catalog records.
- **Analysis service:** Node.js TypeScript service. Hono provides liveness and
  readiness endpoints; a separate command collects Telegram posts, analyzes
  them with OpenAI Structured Outputs, and persists structured presentation
  candidates.
- **Telegram client:** GramJS with a pre-authorized user `StringSession`.
- **Persistence:** PostgreSQL with pgvector, Prisma ORM, and Prisma Migrate.
- **LLM boundary:** the official OpenAI JavaScript SDK and Responses API use an
  explicit server-side key, strict Structured Outputs, and `store: false`.
- **Containers:** Dockerfile for the service; Docker Compose for the service and
  PostgreSQL.
- **Production hosting:** one Railway project and production environment with
  four visible services: public `web`, public read-only `api`, private managed
  PostgreSQL, and private twice-daily `parser` cron. The API and parser use the
  existing service image with different entry points.
- **Configuration boundary:** the collector's public channels come only from
  `TELEGRAM_CHANNELS`. Credentials and the Telegram session also come only from
  environment variables and are never committed.
- **Data boundary:** Telegram post bodies and raw OpenAI responses are transient
  and are never stored. PostgreSQL retains structured presentation candidates,
  source provenance, and minimal analysis/idempotency metadata. The website
  never imports Prisma or connects directly to PostgreSQL.
- **Production content boundary:** `TELEGRAM_CHANNELS` is the only manually
  configured source list. Production has no hard-coded catalog, channel metadata,
  facets, counts, fixture fallback, or seeded prototype corpus. The parser writes
  PostgreSQL, the API reads PostgreSQL, and the web reads the API. An empty
  database renders an honest empty state.

## Scope of the analysis plan

Plan 003 implements the core collection-and-analysis loop. It reads each public
channel post transiently, uses OpenAI Structured Outputs to decide whether the
post presents a project, tool, library, service, product, feature, or other
technology subject, and saves structured presentation candidates only when
relevant. A minimal per-post ledger is retained for provenance, edits, cursor
safety, and avoiding duplicate API charges.

The plan deliberately does not store Telegram message bodies, raw prompts, or
raw model responses. This clarification supersedes the raw-message archive
references in `business-plan.md:177` and `business-plan.md:193`; reconcile the
business plan separately instead of reintroducing raw-message storage.

The configured channel environment variable is authoritative:

- `TELEGRAM_CHANNELS` is a comma-separated list of public Telegram handles.
- Adding a handle enables/upserts it on the next run.
- Removing a handle disables future collection but never deletes its analysis
  ledger, presentation candidates, or cursor.
- Empty, duplicate, malformed, or private/session-dependent entries fail
  configuration validation before any network call.

plain indexed text filtering, not speculative automatic merges or semantic

3. **Operations maturity** — alerts, SLOs, restore drills, cost budgets, and

## Findings considered and rejected

- **Put all work in one implementation file:** rejected because monorepo
  scaffolding, retrieval UX, and MTProto ingestion have different risks,
  verification gates, and credentials.
- **Build the collector before the website gate:** rejected because it
  contradicts the approved Phase 0 purpose and spends the most effort before
  validating retrieval.
- **Run Telegram synchronization inside the Hono request process:** rejected
  because scheduler retries or multiple replicas could create overlapping runs.
  The same package/image exposes a separate one-shot `sync` command.
- **Archive raw Telegram messages before analysis:** rejected after the
  clarified core requirement. Post bodies remain transient; only structured
  presentations and a minimal processing ledger are durable.
- **Store the channel list in source code or the database UI:** rejected because
  the owner explicitly selected environment-driven channels and the public
  website is read-only.
- **Add an admin website, authentication, analytics, or payments:** rejected as
  contrary to the business plan.
- **Keep the curated web corpus as a production fallback or seed:** rejected
  because production must contain only catalog data created by parsing configured
  Telegram channels. Empty and failed upstream states must remain visible.
- **Create separate Railway projects for web, API, parser, and PostgreSQL:**
  rejected because one project already provides service isolation, reference
  variables, private networking, and a single production environment.
